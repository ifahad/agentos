# Cycle 3 backlog — console information design

Structural findings noticed during the Cycle 2 visual sweep. None were fixed
there: Cycle 2 is visual-only, which is what keeps rendering sufficient as its
verification.

| Page | Finding |
|---|---|
| Users | Panel subtitle reads "Inviting a user issues a one-time agu- token; removing one revokes it." — `agu-` is not a word; the copy looks like it lost a fragment during an edit (`pages/Users.tsx:106`). Needs a copy fix, not a colour one. |
| Overview, Keys, Audit, Orgs, Users, Secrets, Provisioning | With no admin key configured, these seven pages render nothing but the "No admin key configured" notice — no scaffold, form, or preview of what the page shows once configured. Documents, Improve, Multiverse and Operators, by contrast, keep their full panel structure visible alongside the same notice. Worth deciding, page by page, whether the quieter pages should do the same or whether the blank page is intentional. |
| ui/Field.tsx | `Input` renders `<input {...rest} />` with no `type` attribute and no default, so an `<Input>` used without an explicit `type` prop produces a bare `<input>`. `styles.css`'s form styling is keyed on `input[type="text"], input[type="number"], input[type="password"], input[type="search"]`, so none of those selectors match it and the shared background/border/focus-ring never applies. PRE-EXISTING — identical at this cycle's base — and the fix is behavioural (either default `type="text"` in the component or add a bare `input` selector), so it was out of scope for a visual-only cycle. Whichever way it is fixed, re-measure the focus ring and field contrast afterwards. Binding `color-scheme` to the theme means those bare inputs now take UA dark styling on the dark theme; their placeholder text measures **2.43:1** against the UA field background, below the 4.5:1 floor. Scope is 3 inputs on 2 routes — one on `/multiverse`, two on `/operators`. Label and value text are unaffected. This is not a regression for users on a dark-preference OS, who were already at 2.43:1; it affects only light-preference-OS users, who in exchange stopped seeing a glaring white input box on the near-black ground. Fixing `Field.tsx` to emit an explicit `type` resolves it, at which point the console's own field styling applies and the placeholder should be re-measured. |
| ui/motion.ts, styles.css | Duration drift: `DUR_FAST = 0.12` / `DUR_MED = 0.2` (seconds, framer-motion) against `--dur-fast: 110ms` / `--dur-med: 180ms` (CSS). JS transitions and CSS transitions on the same element therefore run at slightly different speeds. Cycle 2 corrected the comments to state the truth but deliberately left the numbers alone, since changing them alters feel. PREFERRED FIX: have `motion.ts` READ the custom properties (`getComputedStyle(document.documentElement).getPropertyValue("--dur-fast")`, parsed to seconds) rather than hard-code a third set of constants — one source of truth, and it inherits the `prefers-reduced-motion` block that already zeroes them. |
| Console-wide (tooling) | No automated NON-TEXT contrast check exists. `scripts/render.py` measures text nodes only, so borders, focus rings, meter fills, pill edges and scrims are all unguarded — three separate sub-3:1 border defects this cycle (`.btn:hover`, `.btn.danger`, and the light scrim) were each found by hand. REQUIREMENT for whoever builds it: it MUST composite OVERLAPPING ABSOLUTELY-POSITIONED SIBLINGS, not only ancestor backgrounds. The current harness's `bgOf` walks up the ancestor chain, which is why it could not have caught `.ui-tab.active` (label on `--v2`) sitting over `.ui-tab-pill` (`background: --v`) at 1.66:1 — the pill is the label's SIBLING, so no ancestor walk ever sees it. Same shape as `.nav-pill` and `.docs-rail-pill`. |
| Sidebar | `.nav-note-hold` no longer carries the `--hold` hue. It was moved to neutral ink during the Cycle 2 contrast sweep because `--hold` cannot clear 4.5:1 as small text on any light surface. The consequence is that "held" now survives only in the WORDING of the note, with no colour cue — the one place in the console where a hold state is stated without being signalled. Worth revisiting with a treatment that carries the hue somewhere non-text (a border or a dot, where the 3:1 floor applies) rather than restoring failing text. |
| Documents, Improve | Primary action buttons ("Ingest document", "Run evals", "Propose improvement") stay enabled with empty required fields and only disable while the request is in flight. Playground ("Run"), Multiverse ("Queue") and Operators ("Create operator") disable until required input is present, in addition to disabling in flight. The two groups validate differently; worth picking one convention. |
| Users, Overview (and every `EmptyState` behind a failing fetch) | An `EmptyState` asserts emptiness even when the fetch that would have filled it failed, so an error notice and a "there is nothing here" message stack on the same panel. Measured with an admin key set: `/users` with `/admin/orgs` 200 and `/admin/orgs/{id}/users` 500 renders the red `HTTP 500 (error, HTTP 500)` notice directly above `No users yet — A user is a member of this org with a role…`; `/` as a non-root member with `/admin/keys` 403 renders `No budgets set — A budget caps how much a key can spend per month…`. The panel summaries on those same panels were fixed to stay silent in exactly these states (2026-08-02 information-design cycle), so the two components now disagree: the summary says nothing, the body says "nothing exists". Deliberately NOT patched at the end of that fix wave — how an error state and an empty state should compose (does the error replace the empty state, sit above a neutral "could not load" body, or something else?) is a design question for every page at once, not a per-call-site conditional. |
| Users, Provisioning | The org `<select>` placeholder reads `no admin key` when the org list has not been fetched, which names a cause that is wrong in one reachable state: a key IS set but is failing. Measured with a wrong key in localStorage and 401 on every `/api/**` — `/users` and `/provisioning` both show `select[Org]: ['no admin key']`. This is an improvement on the prior `no orgs`, which claimed a measured emptiness the console never had (fixed 2026-08-02), so it no longer asserts a count; but a state-neutral phrasing (or one that distinguishes "not configured" from "could not load") would be truer. Left for the same reason as the row above: the honest wording depends on how error and empty states are decided to compose console-wide. |
| Overview | When `/admin/usage` returns 401 but `/admin/audit` returns 200, the Requests tile renders an em dash with `aria-label="Not available"` while a populated 24-hour request sparkline is drawn beside it. Cause: `console/src/ui/Stat.tsx:45-48` renders the `spark` slot unconditionally, and the sparkline is fed by the audit resource rather than by the usage resource that gates `unavailable`. Neither element lies — each is individually provable — but the pairing reads ambiguously. This state became reachable only when tile gating moved from `!adminKey` to the usage fetch resolving; under the old gating, no key disabled both resources at once so the combination could not occur. |
| Users | On `/users` as root, switching from an org whose members fetch succeeds to one whose fetch returns 500 leaves `Members` reading the previous org's count (e.g. `2 members`) and the table showing the previous org's rows, beneath a red `HTTP 500` notice. Cause: `useLoad` (`console/src/components/common.tsx:63-90`) sets `data` only in `.then` and never clears it when its deps change or when the loader rejects, so `usersLoad.data != null` remains true and holds a real reading that belongs to a different org. Not a regression — identical behaviour before the fix commits, which closed only the case where the retained value was a `Promise.resolve([])` placeholder rather than a real array. Worth noting that the fix's own comment ("useLoad does not clear data when its deps change") implies this case without covering it. The fix would be to clear `data` on a dep change in `useLoad`, which is a shared-hook change affecting every consumer and so needs its own pass. |
