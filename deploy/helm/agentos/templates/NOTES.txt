READ THIS BEFORE EXPOSING THE CONSOLE
─────────────────────────────────────
The console proxies /api/runtime/ with the runtime bearer injected server-side.
That is what keeps the token out of the browser — and it means the proxy asks
the caller for nothing. Anything that can open a TCP connection to the console
Service can run an agent:

  curl -X POST http://<console>/api/runtime/runs -d '{"input":"..."}'

returns 200 and executes. That reaches agent runs, the code sandbox, every
connected MCP tool, and spend against the runtime key. The console's own
sign-in is client-side only; it does not gate this path. By contrast
/api/gateway/ authenticates every request itself, so the two paths are not
equally protected and the difference is easy to miss.

Treat the console Service as an administrative surface:
{{- if .Values.ingress.enabled }}

  !! The console is published at {{ .Values.ingress.host }}{{ .Values.ingress.path }}
     You set ingress.frontedByAuth=true, asserting that SSO, mTLS or an IP
     allowlist authenticates in front of it. The chart cannot verify that.
     If it is not true, everything above is reachable by anyone who resolves
     that host.
{{- else }}

  ingress is disabled (the default), so the console is reachable only in-cluster
  — use port-forward. Enabling it requires ingress.frontedByAuth=true, which is
  your assertion that something authenticates in front.
{{- end }}

  Full model: docs/security/trust-boundaries.md
